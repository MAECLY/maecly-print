# IPC and CLI

> **TL;DR** — The Tauri webview talks to the Rust core via typed `invoke()` commands. A headless CLI mode for the same Rust binary (launched with `--cli` or any subcommand) is planned for M1 — see §3. It will share the same handlers in `src/ipc/`, so anything you can do in the dialog you will be able to do from a script; JSON output mode (`--json`) will make it scripting-friendly. Exit codes are documented.

## 1. Two surfaces, one core

```
+-------------+    invoke()    +------------------+   handlers   +---------------+
| Webview UI  | -------------> | Tauri command    | -----------> | Rust modules  |
| (React)     |                | bridge           |              | (queue,       |
|             |                | (src/ipc/)       |              |  engine, etc.)|
+-------------+                +------------------+              +---------------+
                                       ^                                ^
                                       |                                |
                                  +----+----------+                     |
                                  | clap CLI      |                     |
                                  | (planned, M1) |---------------------+
                                  | (src/cli/)    |
                                  +---------------+
```

The Rust modules expose a service trait. The IPC bridge implements a thin adapter that translates input (JSON args) into service-trait calls and translates output (Result types / domain values) into JSON for the webview. The CLI (planned, M1 — see §3) will add a sibling adapter doing the same for argv in and stdout out.

## 2. Tauri IPC commands

All commands live under namespace `app:` (auto-derived) and are declared with `#[tauri::command]`. TypeScript bindings are generated by `tauri-specta` into `src/ipc/bindings.ts`.

> **Wired today (M1).** Every row above is registered via `tauri_specta::collect_commands!` (`src-tauri/src/lib.rs`): the **diagnostic** (`app_info`, `open_logs_folder`, `report_issue`, `open_external`), **printer**, **jobs/queue**, **profiles**, **settings** (`get_app_settings`/`set_app_settings`), and **update** (`check_for_updates`) commands. Profiles are now a real persisted backend (`profiles.toml` + `ipc::profiles`), not the frontend-local presets of earlier drafts. The only update/settings commands *not* yet registered are the **M4** installer path — `install_update`, and the earlier `get_settings`/`update_settings` design was superseded by `get_app_settings`/`set_app_settings` (see the decisions below).
>
> **Contract decisions worth calling out** (the shipped surface diverges from earlier drafts of this doc):
> - **Settings are replace-sections, not deep-merge.** `set_app_settings` overwrites each of the four wire sections wholesale with what the client sends (keeping `printers` + `schema_version`). It is *not* the field-level `update_settings(patch: Partial<Config>)` deep-merge sketched previously; that command does not exist. The client sends a complete `AppSettings`.
> - **`list_profiles` ordering is built-ins-first, then customs by name** — not a flat name sort. The three built-ins always lead in canonical order (`Quick`, `Duplex BW`, `Photo Color`), then customs case-insensitively by name.
> - **`save_profile` is an upsert with id-preservation semantics** (see the row above), which is what makes a client-side "undo delete" restore the same id.
> - **There is no `duplicate_profile` command.** Cloning/duplicating is a client-side draft (a new profile with an empty id) that `save_profile` creates; the backend has no dedicated duplicate verb.

### 2.2 Type definitions

```ts
// src/ipc/bindings.ts
export type PrinterInfo = {
  name: string;
  port: string;
  driver: string;
  is_default: boolean;
  is_local: boolean;
  status: PrinterStatus;
};

export type PrinterStatus =
  | "ready" | "offline" | "paused" | "out_of_paper"
  | "out_of_toner" | "jammed" | "needs_attention";

// --- Print settings (job.rs; lowercase wire enums) ---
export type Duplex      = "none" | "long" | "short";
export type ColorMode   = "color" | "monochrome";
export type PaperSize   = "a4" | "letter" | "legal" | "a3";
export type Orientation = "auto" | "portrait" | "landscape";
export type Scaling     = "fit" | "shrink" | "none";

export type JobSettings = {
  printer: string | null;        // null → app/OS default resolved at dispatch
  duplex: Duplex;
  color_mode: ColorMode;
  copies: number;                // 1..=999
  paper_size: PaperSize;
  orientation: Orientation;
  scaling: Scaling;
  page_ranges: string | null;    // "1-5,8" or null for all pages
};

// N files sharing one resolved settings bundle. `profile_name` is display/log
// only — dispatch uses the resolved `settings`, not a backend profile lookup.
export type PrintRequest = {
  files: string[];
  settings: JobSettings;
  profile_name: string | null;
};

export type JobBatch = { batch_id: string; job_ids: string[] };

export type JobState =
  | "queued" | "converting" | "converted" | "printing"
  | "done" | "failed" | "paused" | "cancelled";

export type JobError    = { code: string; message: string };
export type JobProgress = { phase: string; percent: number };

export type Job = {
  id: string;                    // UUID v7 (time-sortable)
  batch_id: string;
  state: JobState;
  input_path: string;
  file_name: string;
  input_ext: string;             // lowercased, no leading dot
  input_bytes: number;
  pages: number | null;
  cache_pdf: string | null;      // converted PDF in the cache, once produced
  settings: JobSettings;
  profile_name: string | null;
  printer_resolved: string | null;  // printer chosen at dispatch time
  attempts: number;
  error: JobError | null;
  progress: JobProgress | null;
  submitted_at: string;          // RFC 3339 UTC
  started_at: string | null;
  finished_at: string | null;
};

export type QueueSnapshot = {
  schema_version: number;
  queue_paused: boolean;
  jobs: Job[];
};

// Per-file inspection for the print dialog (jobs.rs).
export type FileInfo = {
  path: string;
  name: string;
  ext: string;                   // lowercased, no dot; "" when none
  bytes: number;
  pages: number | null;
  supported: boolean;
  reason: string | null;         // why unprintable, when !supported
};

// --- Profiles (profiles/mod.rs). `builtin`/`default` are server-computed and
//     ignored on input; `duplex`/`quality` use the profile vocabulary, distinct
//     from JobSettings' engine `Duplex`. ---
export type ProfileDuplex = "off" | "long-edge" | "short-edge";
export type Quality       = "draft" | "normal" | "high";

export type Profile = {
  id: string;                    // built-in slug, or a UUID v7 for customs
  name: string;                  // 1..=100 chars, unique case-insensitively
  builtin: boolean;              // computed: id names a built-in
  default: boolean;              // computed: id === engine.default_profile
  printer: string;               // printer id, or "<default>" sentinel
  color_mode: ColorMode;
  duplex: ProfileDuplex;
  copies: number;                // 1..=999
  paper_size: PaperSize;
  orientation: Orientation;
  scaling: Scaling;
  page_range?: string;           // omitted for "all pages" (no "all" sentinel)
  quality: Quality;
  tray: string;
};

// --- App settings (settings/mod.rs). The four wire sections of config.toml;
//     `printers` and `schema_version` are excluded and preserved server-side. ---
export type Theme         = "light" | "dark" | "system";
export type Density       = "comfortable" | "compact";
export type UpdateChannel = "stable" | "beta" | "nightly";

export type AppCfg = {
  locale: string;
  theme: Theme;
  launch_minimized: boolean;
  density?: Density;             // serde default "comfortable"
};
export type EngineCfg = {
  max_concurrent_conversions: number;   // 1..=8 (applied at next start)
  conversion_timeout_seconds: number;   // 0 disables, else 10..=3600

  config_dir: string;
  log_dir: string;

  version: string;
  notes: string;
  pub_date: string;
  size_bytes: number;
```

### 2.3 Rust handler example

```rust
// src-tauri/src/ipc/jobs.rs
use tauri::State;
use crate::queue::job::{JobBatch, PrintRequest, QueueSnapshot};
use crate::queue::QueueHandle;

#[tauri::command]
#[specta::specta]
pub async fn print_files(
    state: State<'_, QueueHandle>,
    req: PrintRequest,
) -> Result<JobBatch, IpcError> {
    // `submit` validates and fans the batch out synchronously (off the IPC
    // thread), returning before any job is enqueued — a bad request never
    // reaches the queue. The dispatcher then drives the jobs and pushes
    // `queue-updated` events.
    let handle = state.inner().clone();
    run_blocking(move || handle.submit(req)).await
}

#[tauri::command]
#[specta::specta]
pub async fn queue_status(state: State<'_, QueueHandle>) -> Result<QueueSnapshot, IpcError> {
    Ok(state.snapshot()) // reads the dispatcher's live in-memory state directly
}
```

### 2.4 Events (push from Rust to UI)

| Event name           | TS type / payload                             | Emitted by                                  | Status       |
| -------------------- | --------------------------------------------- | ------------------------------------------- | ------------ |
| `queue-updated`      | `QueueUpdated` = `QueueSnapshot`              | Dispatcher, on every persisted mutation (submit / transition / cancel / clear / pause) | shipped |
| `job-progress-event` | `JobProgressEvent` = `{ id, phase, percent }` | Dispatcher's conversion progress callback; throttled ≥ 100 ms, advisory, **not** persisted | shipped |
| `update-available`   | `UpdateInfo`                                  | Updater on a successful check               | planned (M4) |
| `update-progress`    | `{ downloaded: number, total: number }`       | Updater during download                     | planned (M4) |

The two shipped events derive `tauri_specta::Event` (collected in `src-tauri/src/lib.rs`), so their names and payload types are generated into `src/ipc/bindings.ts`. The event *names* are the struct identifiers kebab-cased by the derive (`QueueUpdated` → `"queue-updated"`, `JobProgressEvent` → `"job-progress-event"`). The webview subscribes through the generated `events` object — `events.queueUpdated.listen(...)` / `events.jobProgressEvent.listen(...)` — not raw `listen()`. (The `printer-changed` event listed in earlier drafts is not implemented.)

### 2.5 Capability declaration

Tauri 2's capability system gates **core and plugin** permissions (window, webview, dialog, shell, …) per window. It does **not** gate the app's own `#[tauri::command]` handlers: commands registered through `tauri_specta::collect_commands!` / `invoke_handler` (`src-tauri/src/lib.rs`) are the application's private IPC surface and are callable from the main window regardless of the capability list. So `capabilities/main.json` carries only the core defaults plus the one plugin permission we actually use:

```json
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "main-capability",
  "description": "Permissions granted to the MaeclyPrint main window.",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "core:window:default",
    "core:webview:default",
    "dialog:default"
  ]
}
```

`dialog:default` grants the native file-picker plugin the Print Job screen uses. The defense-in-depth boundary for the app's own commands is therefore twofold, and does **not** come from a per-command allowlist:

1. **Closed surface.** Only the commands enumerated in `collect_commands!` exist at all — there is no dynamic or third-party command surface for a compromised webview to reach.
2. **No remote code.** The window's CSP loads only the bundled SPA and forbids remote content (see [`security-model.md`](./security-model.md) § 3.3), so there is no attacker-controlled script in the webview to call them in the first place.

## 3. CLI

> **Status: planned, not yet implemented (M1).** The command surface below is the designed CLI contract. It is **not** wired up yet — the current binary runs the GUI only; there is no `--cli` mode, no `clap` subcommands, and no `src/cli/`. This section documents the intended shape (targeted around the M1 "Print Core" milestone); treat every command here as a specification, not a shipped feature. Most IPC commands the mapping in §3.5 targets are live today (jobs/queue, printers, profiles, settings, and the read-only `check_for_updates`); only `install_update` remains planned (M4) — see the "Wired today" note under §2.1.

### 3.1 Entry point

The same binary detects CLI mode by inspecting `argv`:

- If the first non-flag argument is a known subcommand (`print`, `profiles`, `queue`, `update`, `printers`), or `--cli` is present → CLI mode.
- If `--invoke=context-menu` is present → context-menu mode (just opens the dialog with the supplied files).
- Otherwise → GUI mode (open the main window).

### 3.2 Command reference

```
maeclyprint print --files <FILES> [--profile <NAME>] [--printer <NAME>]
                  [--color | --mono] [--duplex <off|long-edge|short-edge>]
                  [--copies <N>] [--paper <A4|Letter|...>] [--range <SPEC>]
                  [--scale <fit|shrink|actual>] [--quality <draft|normal|high>]
                  [--no-dialog] [--wait]

maeclyprint profiles list [--json]
maeclyprint profiles show <NAME-OR-ID> [--json]
maeclyprint profiles create --name <NAME> [--from <NAME>]
                            [--printer <NAME>] [--color | --mono] [...other flags]
maeclyprint profiles delete <NAME-OR-ID>
maeclyprint profiles set-default <NAME-OR-ID>

maeclyprint printers list [--json]

maeclyprint queue status [--json] [--watch]
maeclyprint queue cancel <JOB-ID>
maeclyprint queue cancel-all

maeclyprint update check [--json]
maeclyprint update install [--yes]
maeclyprint update channel [stable|beta|nightly]

maeclyprint --version
maeclyprint --help
```

### 3.3 Flag semantics

- `--files` accepts a comma-separated list of paths and/or globs (`"*.pdf"`, `"~/Docs/*.docx"`). Globs are expanded by the CLI itself, not the shell, so they work on Windows.
- `--no-dialog` skips the GUI and prints immediately with the provided settings (useful for scripts).
- `--wait` blocks until all jobs reach a terminal state, then exits with the worst exit code among them.
- `--json` switches structured commands (`list`, `status`, `check`) to JSON output.

### 3.4 Examples

```
# Print every PDF in a folder using the default profile
maeclyprint print --files "C:\Reports\*.pdf"

# Print one DOCX with explicit overrides, wait for completion
maeclyprint print --files report.docx --printer "HP LaserJet" \
    --duplex long-edge --color --copies 2 --no-dialog --wait

# Pipe-friendly listing
maeclyprint printers list --json | jq -r '.[] | select(.is_default) | .name'

# Watch the queue
maeclyprint queue status --watch

# Force an update check, install if available, no prompt
maeclyprint update check --json
maeclyprint update install --yes
```

The CLI implementation in `src/cli/` is intentionally a thin wrapper that calls the same underlying service traits as the IPC handlers. Both surfaces stay in sync because of this.

### 3.6 JSON output mode

With `--json`:

- `list`-style commands emit a JSON array.
- `status`-style commands emit a JSON object.
- Errors emit `{"error":{"code":"...","message":"..."}}` to stderr and exit with the matching exit code below.

Without `--json` we emit human-friendly tables (using `comfy-table`).

### 3.7 Exit codes

| Code | Meaning                                                              |
| ---- | -------------------------------------------------------------------- |
| 0    | All requested operations succeeded.                                   |
| 1    | Generic error (catchall).                                            |
| 2    | Invalid command-line usage.                                          |
| 3    | Configuration error (unreadable / invalid `config.toml` etc.).        |
| 4    | Profile not found / invalid.                                         |
| 5    | Printer not found / invalid.                                         |
| 6    | One or more files not found / unreadable.                            |
| 7    | One or more files unsupported.                                       |
| 8    | Conversion failed (timeout or converter error).                       |
| 9    | Printing failed (spooler reported error).                             |
| 10   | Update check failed (network/signature).                             |
| 11   | Update install failed.                                               |
| 12   | User cancelled.                                                      |
| 64+  | Reserved for future use; never overlap with `sysexits.h`.            |

For batches, the worst (highest) exit code among jobs is returned.

## 4. Error model

A single `IpcError` enum is serialized to the webview today and will be serialized identically once the CLI (§3) lands:

```rust
#[derive(thiserror::Error, Debug, Serialize)]
#[serde(tag = "code", content = "message")]
pub enum IpcError {
    #[error("File not found: {0}")]
    FileNotFound(String),
    #[error("Invalid request: {0}")]
    InvalidRequest(String),
    #[error("Unsupported file format: {0}")]
    UnsupportedFormat(String),
    #[error("Conversion failed: {0}")]
    ConversionFailed(String),
    #[error("Printing failed: {0}")]
    PrintFailed(String),
    #[error("Unsupported setting: {0}")]
    UnsupportedSetting(String),
    #[error("Missing dependency: {0}")]
    DependencyMissing(String),
    #[error("Job not found: {0}")]
    JobNotFound(String),
    #[error("Invalid state: {0}")]
    InvalidState(String),
    #[error("Profile not found: {0}")]
    ProfileNotFound(String),
    #[error("Update check failed: {0}")]
    UpdateCheckFailed(String),
    #[error("Internal error: {0}")]
    Internal(String),
}
```

Webview receives `{"code":"FileNotFound","message":"foo.pdf"}`. The planned CLI (§3) will print the `Display` form to stderr unless `--json`, in which case the same JSON is written to stderr.

## 5. Stability

- IPC command names and event names are part of the **public surface** of MaeclyPrint and follow semver. Renaming or removing one is a major version bump.
- CLI subcommand names and flags are public surface. New flags can be added in minor versions; existing flags may be deprecated (with a warning) and removed only in a major version.
- JSON output schemas are public surface and versioned implicitly by app version. A `--cli-protocol-version` flag may be added in 2.x.
